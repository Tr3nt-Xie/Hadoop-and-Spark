# Extension: how do Hadoop and Spark scale with input size?

## Why

The graded suite (`benchmark-results/`) used a 36 MB input. At that size the
jobs measure start-up cost more than processing:

* Hadoop 1 node: 201.6 s for word count, 230.4 s for min/max. min/max is word
  count plus a second MapReduce job, and that second job alone costs 29 s,
  although it only reads 48,097 lines of counts. That 29 s is almost pure
  fixed cost: a new YARN ApplicationMaster, new containers, new JVMs.
* Spark 1 node: 22.0 s for word count and 21.8 s for min/max. The extra step
  runs inside the same application on data already in memory, so it costs
  nothing measurable.
* With `dfs.blocksize` and the split size at 4 MB, the 36 MB input is 42 map
  tasks, each starting a JVM and a Python process for under 1 MB of text.
* Going from one to two nodes gives Hadoop 1.39x and Spark 1.30x, far from
  2x, which is what fixed per-job cost would produce.

So the 36 MB numbers answer "which starts faster", not "which processes
faster". This experiment separates the two by measuring the same jobs at
three sizes and fitting, per framework and node count,

    time = fixed + size / throughput

## Method

Same code, same validation and same cluster layout as the graded suite:

* Inputs of 32 MiB (the graded size, re-measured on the same run), 256 MiB
  and 1 GiB, generated by `scripts/prepare_data.py --minimum-mib N` on each
  node independently; the two manifests are compared before loading, so no
  gigabyte passes through the laptop.
* Hadoop and Spark, one and two nodes, all three jobs, every output checked
  against the reference answers by `scripts/benchmark.py`.
* Two-node runs load half the files from each node, as in the graded suite,
  so both DataNodes hold local blocks.

`scripts/aws_provision.sh` creates the two nodes in an AWS account (Ubuntu
22.04 t3.medium with Unlimited CPU credits, so long runs are not throttled the
way the graded t2.medium master nearly was; 30 GB gp3; SSH from the caller's
IP only) and writes `.local/cluster.json`. `scripts/extension_scaling.sh`
then runs the matrix and leaves each run directory in `results/`.

```bash
AWS_PROFILE=lab4 bash scripts/aws_provision.sh          # or use an existing cluster.json
python3 scripts/cluster.py deploy
SIZES="32 256 1024" REPS=1 bash scripts/extension_scaling.sh
python3 scripts/cluster.py download
AWS_PROFILE=lab4 bash scripts/aws_provision.sh stop     # or destroy
```

Expected cost: two t3.medium for about three hours, under USD 1.

## What each outcome would mean

* If Hadoop's time grows much more slowly than 8x from 32 MiB to 256 MiB, the
  graded numbers were dominated by fixed cost, and the "Spark is 9x faster"
  headline shrinks at realistic sizes.
* If Hadoop's two-node speedup rises toward 2x at 1 GiB, the 1.39x in the
  graded suite was fixed cost, not a lack of parallelism.
* If Spark keeps a large throughput advantage at 1 GiB, that is the effect of
  in-memory processing proper: map output that Hadoop spills to local disk
  and shuffles through files stays in executor memory in Spark.
* The min/max gap is the cleanest single measurement of the difference: in
  Hadoop it is one extra job's start-up; in Spark it is one extra in-memory
  stage.
